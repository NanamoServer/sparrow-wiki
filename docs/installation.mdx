Install the same Sparrow JAR on your proxy and backend servers, then configure server IDs, Redis, and persistent storage.

## Requirements

**Sparrow requires a proxy, even with only one backend server.** Use one Velocity or BungeeCord/Waterfall proxy per Sparrow network. Multi-proxy setups are not supported.

Sparrow supports Paper and Folia from **1.21.11**. For Spigot, use **26.2 or a newer adapted version**. Match the server version to the Sparrow build you install.

Install the Java version required by your Minecraft server (Java 21 or later). PlaceholderAPI is optional: install it to parse external placeholders or use Sparrow's [Home placeholders](./features/home.mdx#placeholderapi). Home commands work without it. LuckPerms is also optional; with it installed, [Maintenance](./features/maintenance.mdx) and [Player limit](./features/player-limit.mdx) use LuckPerms permissions to decide who can bypass them before joining. Without it, only operators can bypass.

**Redis and one persistent database are required at startup.** Choose MongoDB, MySQL, MariaDB, or PostgreSQL.

<Admonition type="warning" title="Storage service versions">

Redis requires **7.2.4 or newer**. MySQL requires **8.0.0 or newer**.

</Admonition>

## Install

Sparrow uses one universal file, `sparrow-<version>.jar`. Put the same version in the `plugins/` folder of the proxy and every backend, then start them to generate configuration files. Each backend creates its settings under `plugins/sparrow/`:

## Server ID

Change the existing `server-id` in `plugins/sparrow/server.yml`:

~~~yaml title="server.yml · Server ID"
server-id: 'lobby'
~~~

Every server sharing Redis and storage needs a different ID, such as `lobby`, `survival-1`, or `survival-2`. The ID must match the backend name configured on the proxy. Change this value when copying configuration to another server.

Sparrow refuses to start if another running server already uses that ID. If a server has just crashed, wait about 4 seconds before starting it again with the same ID.

## Redis and database

The following snippets show only connection settings. **Do not replace the whole file with them.** Keep the generated `__version__` value.

### Redis

~~~yaml title="config.yml · Redis"
redis:
  url: 'redis://localhost:6379/0'
  username: ''
  password: ''
~~~

Set the actual host, port, and credentials. Servers in the same group should use the same Redis database; `/0` selects database 0.

### Persistent storage

The default is `MONGODB`. To use MySQL, create a database and an account with table creation and read/write access, then configure:

~~~yaml title="config.yml · MySQL example"
database:
  type: MYSQL
  mysql:
    url: 'jdbc:mysql://localhost:3306/minecraft?connectTimeout=5000&socketTimeout=10000&characterEncoding=UTF-8'
    username: 'sparrow'
    password: 'your_database_password'
    table-prefix: 'sparrow_'
~~~

Alternatively, select `MARIADB`, `POSTGRESQL`, or `MONGODB` and edit its corresponding section. Servers sharing data need the same database and table prefix. MongoDB uses a shared database name and `collection-prefix`.

Restart, check the console for connection results, and run `/sparrow feature-list` to inspect feature state.

## Proxy plugin \{#proxy-plugin}

Velocity, BungeeCord/Waterfall, and the backend servers all use `sparrow-<version>.jar`. When upgrading from separate platform JARs, remove those old JARs before installing the universal file.

On the proxy, Sparrow creates `plugins/sparrow/config.yml`. Point it at the same Redis as your backends, including the same database number:

~~~yaml title="Proxy config.yml · Redis"
redis:
  url: 'redis://localhost:6379/0'
  username: ''
  password: ''
~~~

Enable the player information forwarding mode appropriate for your proxy and backends. All players should connect through the proxy address. Restart the proxy after editing; the console shows `Connected to Redis` when the Redis connection works.

`/kick` and [bans](./features/ban.mdx) disconnect players from the whole network and show the reason. [Warps](./features/warp.mdx), [Homes](./features/home.mdx), [Spawn](./features/spawn.mdx), [Back](./features/back.mdx), and [teleport requests](./features/tpa.mdx) can send players between the connected backends.

## Features and commands

`features.yml` controls features; `commands.yml` controls which commands exist, their entry points, and their permissions. For example:

~~~yaml title="features.yml · Patrol"
patrol:
  enabled: true
  skip-spectators: true
  excluded-worlds: []
~~~

~~~yaml title="commands.yml · Patrol command"
patrol:
  enable: true
  usages:
    - /sparrow patrol
    - /patrol
  permission: sparrow.command.patrol
~~~

Features use `enabled`; commands use `enable`. Disabling an entry point and disabling its feature are separate actions. A command turned off in `commands.yml` does not exist on the server at all, while the commands of a disabled feature are hidden from players and answer with a notice until the feature is enabled again.

| Setting | How to apply |
| --- | --- |
| Feature settings in `features.yml` | `/sparrow reload` |
| Teleport groups in `teleport.yml` | `/sparrow reload` |
| Feature switches | `/sparrow feature-enable <feature>` or `feature-disable`; saved to the file |
| Command switches, entry points, and permissions | Restart |
| Redis, database connections, or `server-id` | Restart |

Set `forced-locale: en_US` in `config.yml` to select the console language. See [Permissions & Commands](./commands.mdx) and the individual feature pages for details.
